# 2026-07-03 — 임베딩 질문에서 역산한 옷 축 실행 규격 (2축 레시피 · 선행 데이터 · 저장 경계 개정 · B2B 배치 · MVP 루프)

## 논의

운영자의 "Gemini Embedding 2 우리도 써볼만하지 않나?" 한 줄에서 출발해, 도구 질문을 제품 구조 질문으로 역산한 세션. 임베딩→유사검색 개념→"볼륨이 뭔데"→"임베딩의 장점이 뭔데"→개인화→닭-달걀→4층 아키텍처→원본 저장→B2B→MVP 제안→생성 로직 확인→"트렌드 반영엔 옷 데이터가 선행해야 한다는 아이러니"→선행 데이터 규격→저작 규격→레시피 정체성(2축)→트렌드 판정기 순으로, 운영자가 매 턴 개념을 파고들며 에이전트 프레임을 두 번 정정. 결과는 STRATEGY §11로 고정.

## 진행 결

- **임베딩 = 라우팅 층의 미래 부품, 지금 도입 안 함.** 모선에 이미 소화된 노트(gemini-embedding-2, 2026-04) 렌즈 재사용: 임베딩 ≠ 인식, = 유사 검색. 장점이 발동하는 조건은 전부 "질의하는 쪽을 우리가 통제 못 할 때"(cross-modal 질의·어휘 불일치·enum 불가 속성) — 현재는 운영자 양쪽 어휘 통제의 닫힌 세계라 발동 표면 없음. 게이트 = 유저 발생(볼륨+질의 개방성), 그때 pgvector + 모델 측정 비교.
- **4층 아키텍처 명명:** 트렌드 레이어 / 기본 데이터 레이어(옷 축에만) / 라우팅 레이어(행동 데이터 발생지 = moat 축적지) / 실행 백엔드. 운영자의 층 직관에서 "백엔드"를 라우팅/실행으로 분리한 것만 수정.
- **운영자 정정 ①: "원본 옷 사진은 있어야 함."** 에이전트가 zero-PII를 과확장("프로필만 저장, 사진은 부채")한 것을 운영자가 반박 → 정정 수용: 생성 시드는 픽셀 요구(프로필=손실 압축)·backfill·커머스 세 근거로 원본 = 자산. 경계 재획정: **옷이 아니라 얼굴**(유저 착용샷은 stage-0 추출본만, 브랜드 컷은 라이선스 축). §10-B가 파킹한 "별도 명시 결정"이 이 턴에서 내려짐 → §11-C.
- **운영자 정정 ②: "인스타/옷 두 축은 별개."** 에이전트의 "사진=포장지, 옷=화물" 결합 프레임을 운영자가 기각 → 레시피 = 트렌드 포스트 단위, 싣는 트렌드는 사진형|옷형|겹치면 결합. **옷 참조 저작 필수 아님** — 씬형도 정당 상품, 강제는 용도 단계(hook·커머스)에서만 → §11-A.
- **닭-달걀 해체:** "유저↑→옷데이터↑" 순서 고정에 운영자가 의문 제기 → 정직한 재정리: 논리 필연이 아니라 **투자 우선순위**(유저 전 코퍼스는 어느 병목도 안 풂 + 재작업·라이선스 선불 비용). 단 hook이 시드 옷을 요구하면 빌드 순서는 뒤집혀도 **결정 순서는 hook 먼저**. 반증 신호("입어볼 옷 없어 이탈")가 잡히면 순서 전환.
- **B2B 배치:** 운영자 "B2B 배제 안 해도 될 듯" → 사실 교정: 배제된 적 없음(ruled-OUT은 자체모델·얼굴수집·A-track). 3슬롯 확정: hook 시드 소싱(롱테일 브랜드, 첫 진입) / velocity 공급 / 트렌드 인사이트 상품(입어봄 = 구매-선행 욕망 신호, 집계 판매, zero-PII). 가드 = 1인 대역폭, 시드 한정 → §11-F.
- **MVP "저장→추천" 제안 → 절반 채택:** 저장 표면(행동 신호+리텐션 앵커) 직관은 채택하되 배치 수정 — 추천은 콜드스타트 최악 기능이라 전면 배치 기각(옷장앱 카테고리 약리텐션 선례). 확정 루프: 생성 코어 / 옷장 = 배기가스 / 추천 = v0 태그 매칭 → §11-F.
- **선행 데이터 규격 확정:** 옷형 레시피용 garment-solo 히어로 컷 **20~40장**(2~4주 런웨이, 상시 10~20 회전) + 장당 §10-B 7칸 프로필 + 권리/브랜드/링크 메타. v0 = `style_reference_key` 직부착, v1 = `garments` 테이블(큐레이션/유저 동일 스키마). 프로필 칸에 enum성/서술성 구분(미래 필터/벡터行) → §11-B·D.
- **트렌드 판정기 승급 경로:** v0 = 운영자 눈+외부 프록시(후행·무차별 한계) → 런칭 후 내부 행동 집계(선행·독점)로 승급. 배관 절반 존재(`generations.recipe_id`), 부족분 = 저장·공유 이벤트 → **hook 구현 범위에 이벤트 스키마 포함**(유일한 시간-민감 항목: 늦으면 판정 데이터 증발) → §11-E.

## 왜 / 교훈

- **도구 질문은 구조 질문의 문고리.** "이 임베딩 모델 쓸까?"에 yes/no로 답하고 끝냈으면 §11의 전부(2축·저장 경계·B2B·판정기)가 안 나왔다. 도입 시점을 따지려면 "무엇을 검색하나"→"코퍼스가 뭔가"→"레시피가 뭔가"까지 역산해야 했고, 그 역산이 실제 산출물.
- **운영자 정정 2건 모두 에이전트의 과확장이 원인:** zero-PII를 "이미지 저장 금지"로(원문은 얼굴 수집 금지), 2축 관계를 "구조적 결합"으로(운영자는 별개 축). 원칙의 *정확한 원문*과 에이전트의 *확장 해석*을 구분할 것 — 확장은 명시 표기 없이 단정으로 내지 말 것.
- **§10-B 반증과의 정합 유지:** 세션 중 에이전트가 "프로필 텍스트가 프롬프트에 들어가야 fit-lock 작동"이라 발언했으나 이는 stale — eval 3라운드가 프로필 주입을 반증(주입 off). 프로필의 소비처는 프롬프트가 아니라 DB적립·칩UX·커머스레일 + (§11-D 신규) 미래 검색 인덱스. fit-lock은 프롬프트 골격의 독립 문구로 별개.
- **트리거(이 회의록):** 운영자 "결론적으로 정리해줘 보고 판단할게" → 판단 슬롯 5건 제시 → #2 명시 ruling + "일단 진행해"로 나머지 기본안 채택 — 판단 슬롯을 표로 몰아 제시한 것이 결정 속도를 만듦.
